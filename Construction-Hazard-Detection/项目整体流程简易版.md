## 2. 数据契约约定（本文使用的关键结构）

## 一、方向 1 / 核心方向 1：工作票文本信息提取（时间、地点、作业内容、安全措施）

1. 整体技术路线

- 图像 → OCR：PaddleOCR 做版面分析和文字识别
- OCR 结果 → NER：BERT-MRC（阅读理解式 NER）按问题模板抽取各类实体
- 全局补充 / 规则抽取：对 OCR+NER 输出进行字符串整体正则处理，补齐时间段、电压等级、票状态、安全措施等
- 低置信度实体 → 多模态/文本 LLM 校验和整合：用大模型对低置信度实体重判 / 过滤
- 最终得到一个结构化的 entities 列表，包含你关心的时间、地点、作业内容、安全措施等要素
  核心入口在工作票服务的统一流水线：

- unified_pipeline.py
  run() 是端到端入口：

- 上层 HTTP 调用在 api_server.py 的 /api/v1/parse_ticket ，收到上传图片后，写入临时文件，然后：

```python
result = unified_pipeline.run(
    str(temp_file_path),
    enable_ollama=enable_llm,
    enable_neo4j=enable_neo4j,
    llm_provider=llm_provider or None,
)
```

接口与数据契约（Ticket API：`POST /api/v1/parse_ticket`，默认在 8011）：

- 请求：`multipart/form-data`
  - `file`: 工作票图片（`image/png` 或 `image/jpeg`）
  - Query：
    - `enable_llm`: 是否启用 LLM（低置信度实体校验 + 关系抽取）
    - `llm_provider`: `ollama` / `aliyun`（可选）
    - `enable_neo4j`: 是否入库 Neo4j（可选）
    - `enable_hazard_sync`: 是否同步到 Hazard DBM（可选）
    - `hazard_site_name`: 需要同步的站点名（可选）
- 响应（核心字段）：
  - `status`: `success` 或 `error`
  - `ocr_json` / `ner_json`: 中间产物路径
  - `ner.entities`: 后处理后的实体列表（含规则补充后的 TimeRange/Voltage/角色等）
  - `llm_results.relationships`: LLM 抽取的关系（启用 LLM 时）
  - `neo4j_write_status`: 是否写入成功（启用 Neo4j 时）
  - `hazard_sync`: 下发工单号到 DB Management 的结果（启用 hazard_sync 时）

2. OCR 阶段：从图片到文本块

- 位置： run() 内调用 PaddleOCR 脚本
  - OCR 命令构造见 unified_pipeline.py ：

```python
ocr_cmd = [
    config.PADDLE_PYTHON,
    config.OCR_PRE_SCRIPT,
    "--image_path",
    str(image_path),
    "--output_dir",
    config.OUTPUT_DIR,
]
_run(ocr_cmd, cwd=Path(config.PADDLE_PROJECT_ROOT))
```

- 输出： config.OUTPUT_DIR / f"{filename}.json" ，结构是「版面块 + 文本」，对应 seed 脚本模拟的格式见 seed_mock_tickets.py ：
  - 每个块有 block_label （如 doc_title / text ）和 block_content （文本内容）
- 用途：这些块给 NER 使用，同时在流水线中也会串联成完整文本 ocr_text 供后续规则抽取、LLM 关系抽取使用

3. NER 阶段：工作时间、地点、作业内容、安全措施等实体

- 位置：同一个 run() 函数中

```
ner_cmd = [
    config.BERT_PYTHON,
    config.NER_SCRIPT,
    "--ocr_json", str(ocr_out),
    "--output_json", str(ner_out),
]
```

- NER 模型：BERT-MRC，在 mrc-for-flat-nested-ner 子项目中，查询配置在 PROJECT_GUIDE.md 里有说明
- NER 输出： \*\_ner.json ，结构类似 test1_ner.json

  - 分块 blocks ，每块的 text 和 entities
  - entities 内部字段： text 、 type （领域类别）、 start 、 end
    这里的 type 是领域 schema，包含你关心的几类：

- 时间： TIME ，在后处理时还会合并为 TimeRange
- 地点： LOCATION
- 作业内容 / 任务：通常记在 WORK_TASK / TASK 类别中（视训练配置）
- 安全措施： SAFETY
- 票号： TicketNo
- 电压： VOLTAGE

4. 规则补充：从整张票文本补齐关键要素

在 NER 输出基础上， unified_pipeline 又做了一层「整票级正则抽取」，集中在一个大方法里（你打开文件时看到的一段）。例如：

- 提取安全措施：在压平文本 compact 上搜索：

```python
for m in re.finditer(r"安全措施\s*[:：]\s*([^\n]+)", compact):
    value = m.group(1) or ""
    for part in re.split(r"[;；。\.，,、]+", value):
        measure = _normalize_entity_text(part)
        ents.append({"text": measure, "type": "SAFETY", "label": "SAFETY"})
```

- 提取时间段（起止时间）：

```python
m = re.search(
    r"自\s*(\d{4}\s*年\s*\d{1,2}\s*月\s*\d{1,2}\s*日\s*\d{1,2}\s*时\s*\d{1,2}\s*分)\s*至\s*(\d{4}\s*年\s*\d{1,2}\s*月\s*\d{1,2}\s*日\s*\d{1,2}\s*时\s*\d{1,2}\s*分)",
    compact,
)
if m:
    start = re.sub(r"\s+", "", m.group(1))
    end = re.sub(r"\s+", "", m.group(2))
    ents.append({"text": f"{start}~{end}", "type": "TIME", "label": "TimeRange"})
```

- 电压等级、电压单位解析等也在这里一并完成（ VOLTAGE ）
  这一步的作用：保证即使 NER 有遗漏，这些关键字段也能从整体文本的模式中补出来，形成统一的 ents 列表，最后塞回 result["ner"]["entities"] 中。

5. LLM 低置信度实体校验（提升可靠度）

- 入口： enable_ollama=True 时执行（参数名虽然叫 ollama ，但实际 llm_provider 支持 ollama / aliyun ）

```python
if enable_ollama:
    print("正在使用大模型进行低置信度实体校验...")
    validated_entities = validate_low_confidence_entities(
        entities,
        provider=llm_provider,
    )
    entities = validated_entities
    result["ner"]["entities"] = validated_entities
```

- LLM 调用逻辑在 [ollama_client.py](你之前看过，包含 validate_low_confidence_entities ):

  - 根据置信度阈值筛选实体
  - 为低置信度实体构造 prompt（带上下文票据文本）
  - 调用 LLM 返回新的实体类型 / 是否删除
  - 用启发式规则合并回 entities 列表
    综上： 核心方向 1 在代码里已经形成了一条完整链路：

- 图片 → OCR → NER → 整票 regex 补充 → LLM 校验 → 统一 entities
  这些实体直接包含：

- 工作时间（ TimeRange + TIME ）
- 工作地点（ Location / LOCATION ）
- 作业内容（票名、任务描述等）
- 关键安全措施（ SAFETY ）

## 三、方向 2 / 核心方向 1：作业现场违章行为监测（低时延、高效率）

你这部分是靠「小模型实时检测 + 后处理规则」来实现的。

1. 实时检测主流程

- 核心类： live_stream_detection.py 中的 LiveStreamDetector
- 上层驱动： main.py 中每路流的子进程，会创建 LiveStreamDetector ，轮询视频流帧，调用它的 generate_detections() ：

```python
datas, tracked = await live_stream_detector.generate_detections(frame)
```

- 检测模型：
  - 默认 YOLO11n （小模型，低延迟）
  - 支持 SAHI 裁切推理（针对大图/高分辨率）

2. 数据格式与追踪

generate_detections() 输出：

- datas : [x1, y1, x2, y2, conf, cls]
- tracked : [x1, y1, x2, y2, conf, cls, track_id, is_moving]
  内部逻辑要点：

- Ultralytics YOLO 推理 + track：
  - 小模型在 GPU 上做实时检测，保持高 FPS
- movement_thr 与 prev_centers ：
  - 前后帧中心点距离平方 > movement_thr_sq 时， is_moving = 1
  - 静态机械 / 静止车辆会被过滤（后面 DangerDetector 用到）
    这保证了 实时性 （小模型 + 追踪）和 后续规则判断所需的信息 （运动/静止状态）。

3. 违章行为规则识别

违章识别集中在：

- danger_detector.py
  DangerDetector.detect_danger(datas) ：

- 步骤 0：过滤静止机械/车辆
  - \_filter_static_machinery() ，只保留真实在动的机械/车辆，提高「靠近机械」告警的可靠性
- 步骤 1：归一化坐标 Utils.normalise_data(datas) ，对不同分辨率统一处理
- 步骤 2：收集锥桶多边形 / 电杆多边形，用于区域计算
- 规则 A：人员进入受控区域（cone 区域）
  - check_cone_restricted_area()
  - 判断「人」的 bbox 是否落在由锥桶构成的多边形区域内
  - 违章类型： warning_people_in_controlled_area
- 规则 B：未佩戴安全帽 / 安全背心
  - check_safety_violations() ：
    - 人员类别 cls == 5
    - 安全帽违章 cls == 2
    - 背心违章 cls == 4
    - 统计数量并写入 warnings['warning_no_hardhat'] 、 warnings['warning_no_safety_vest']
- 规则 C：人员靠近机械/车辆
  - check_proximity_violations() ：
    - 使用 Utils.is_dangerously_close 计算「人」与机械/车辆 bbox 之间距离/关系
    - 写入 warning_close_to_machinery / warning_close_to_vehicle
- 规则 D/E：吊车靠近电杆、人员进入电杆管制区

  - check_machinery_near_utility_pole() 、 check_pole_restricted_area() 等
  - 通过构建电杆底部圆形区域并检测机械/人员是否进入
    输出：

- warnings: dict[str, dict[str,int]]
- cone_polygons: list[Polygon]
- pole_polygons: list[Polygon]
  这些 warnings 会进一步映射成「规则 / 等级」，见 examples/violation_records/routers.py 中 \_RULE_DEFINITIONS 和 \_map_rule_violations_from_warnings() ：

- 对 warning_no_hardhat 对应规则 RULE-002 ：未按规定佩戴安全帽，级别「高」
- 对 warning_people_in_controlled_area 对应规则 RULE-001 等

4. 低时延、高效率的实现点

- 模型层：YOLO 小模型 + SAHI 分片，保证 GPU 利用率和 FPS
- 代码层：
  - LiveStreamDetector 的处理间隔动态调整（在 main.py 中根据上一轮耗时自动调节）
  - 违章规则是纯几何运算，无额外模型调用，延迟极低
- 并行：每路流独立子进程 + asyncio 事件循环，避免互相阻塞

5. 违章记录上报接口（Violation Records：`POST /upload`，默认 8002）

检测子进程在形成一次“可上报”的违章事件后，会将证据图与结构化字段一起提交到违章记录服务，便于后续检索、回放和汇总。

- 请求：`multipart/form-data`
  - 必填：`site`、`stream_name`、`image`
  - 可选：`detection_time`、`warnings_json`、`detections_json`、`cone_polygon_json`、`pole_polygon_json`、`agent_report`
- 认证：JWT（服务端会根据 token 中的 `username` 校验是否有该站点访问权限）
- 响应：`{ "message": "...", "violation_id": 123 }`

## 四、方向 2 / 核心方向 2：视觉模型二级复核（小模型 + 多模态大模型协同）

你需要的是：对小模型低置信度或复杂场景，自动把图像帧送到多模态大模型（例如 Qwen-VL）进行复核，降低误报。

这块在 BailianVLRefiner + LiveStreamDetector 中已经形成一个完整异步协同机制。

1. 复核器类：BailianVLRefiner

- 位置： live_stream_detection.py 开头：

```python
class BailianVLRefiner:
    def __init__(
        self,
        *,
        enabled: bool,
        provider: str = 'aliyun',
        api_key: str,
        base_url: str,
        model: str,
        low_conf_threshold: float,
        cache_ttl_sec: float,
        cooldown_sec: float,
        max_concurrency: int,
        timeout_sec: float,
        min_crop_size: int,
        pad_ratio: float,
        allowed_class_ids: set[int] | None,
        class_names: dict[int, str] | None,
    ):
        ...
```

内部关键点：

- low_conf_threshold ：低置信度阈值，比如 0.35 ，低于该值的检测会被认为需要 LLM 复核
- cache_ttl_sec ：缓存有效期，避免同一目标被重复请求
- cooldown_sec ：同一轨迹（track）两次请求之间冷却时间，避免高频调用
- max_concurrency ：最大并发 LLM 请求数，通过 asyncio.Semaphore 控制（你刚打开的那一行环境变量就是配置这个并发度的）
- allowed_class_ids ：只对特定类别（如 hardhat/no_hardhat ）做复核
  内部状态：

- \_cache: dict[int, BailianVLCorrection] ：按轨迹 id 存放大模型纠正结果（新的类别 id + 置信度 + 时间戳）
- \_pending: dict[int, float] ：当前正在请求中的轨迹
- \_last_bbox: dict[int, list[int]] ：轨迹最新 bbox，用于“幽灵检测”（track 消失但大模型结果迟到时，仍然能用 bbox 回填）

2. 与小模型的融合流程

在 LiveStreamDetector.**init** 里，从环境变量读取 LLM 相关配置并实例化 refiner。关键环境变量如下（均在 Construction-Hazard-Detection 进程侧生效）：

（对应代码方法：LiveStreamDetector.**init**）

- `LLM_REFINE_ENABLED`: `1/true/yes/on` 开启
- `LLM_PROVIDER`: `aliyun` 等
- `ALIYUN_API_KEY` / `ALIYUN_BASE_URL` / `ALIYUN_MODEL_NAME`: 大模型配置
- `LLM_REFINE_LOW_CONF_THRESHOLD`: 低置信度触发阈值
- `LLM_REFINE_CACHE_TTL_SEC`: 同一 `track_id` 复核结果缓存 TTL
- `LLM_REFINE_COOLDOWN_SEC`: 同一 `track_id` 冷却间隔
- `LLM_REFINE_MAX_CONCURRENCY`: 并发复核请求数上限
- `LLM_REFINE_TIMEOUT_SEC`: 单次请求超时
- `LLM_REFINE_MIN_CROP_SIZE`: 过小目标不复核
- `LLM_REFINE_PAD_RATIO`: 裁剪 padding 比例
- `LLM_REFINE_CLASSES`: 允许复核的类别集合（逗号分隔；为空表示不限制）

3. 低置信度触发逻辑与异步调用

在 BailianVLRefiner.schedule_for_frame() 内部（你之前看过）：

- 输入：当前帧 frame_bgr ， tracked 列表（含 conf、cls_id、track_id）
- 对每个检测：

  - 若 conf >= low_conf_threshold → 不触发复核
  - 若 class_ids 不在 allowed_class_ids → 不触发
  - 若该轨迹在 \_pending （请求中）或 \_cache （已有结果、仍在 ttl 内）且未到冷却时间 → 不重复发送
  - 否则将该轨迹加入 \_pending ，通过 asyncio.create_task(self.\_refine_one(...)) 异步提交大模型请求
    \_refine_one() ：

- 从原始帧按 bbox 裁剪图像， \_crop_to_base64() 转成 base64
- 构造 prompt， \_make_prompt(yolo_cls_id) 会把小模型类别映射成自然语言描述（如「判断此人是否佩戴安全帽」）
- 通过 \_post_chat_completions() 调用阿里云 DashScope 的兼容模式接口（多模态大模型 Qwen-VL）：
  - call_openai_compatible 被封装在 src.llm_utils 中
- 将 LLM 返回内容解析为 json（后缀、code block 格式都兼容）：

```python
parsed = self._parse_llm_json(content)
self._cache[track_id] = {
    'label': new_id,
    'confidence': new_conf,
    'ts': now,
    'evidence_ts': float(evidence_ts),
}
```

4. 结果回写与误报抑制

在 LiveStreamDetector.generate_detections() 末尾（你检索到的片段）：

```python
if self._vl_refiner is not None and self._vl_refiner.enabled:
    tracked = self._vl_refiner.apply_to_tracked(tracked)
    for j in range(min(len(datas), len(tracked))):
        datas[j][4] = float(tracked[j][4])
        datas[j][5] = int(tracked[j][5])
    self._vl_refiner.schedule_for_frame(frame, tracked, frame_ts)
return datas, tracked
```

- apply_to_tracked() ：
  - 查看 \_cache 里是否有对应 track_id 的纠正结果
  - 若有且未过期，则用大模型的 label/conf 覆盖当前小模型输出（即 second-stage review）
- 覆盖后的检测结果 datas / tracked 会喂入 DangerDetector.detect_danger() ，相当于所有告警都是在“修正后的小模型 + 大模型融合结果”基础上做的
- 这种设计：
  - 大模型只在低置信度 case 触发（避免成本和延迟）
  - 通过 concurrency、ttl、cooldown 精细控制调用频率，保证系统仍然实时
  - 由于大模型有更强语义理解和视觉能力，能更好区分诸如「安全帽 / 头发 / 其他物体」等复杂情况，降低误报率

5. 测试验证

- 在 live_stream_detection_test.py 中有针对 LLM refiner 的测试：

  - test_llm_refiner_schedules_low_confidence_tracks ：构造一个 conf=0.2 的检测，断言 schedule_for_frame() 被调用一次，说明低置信度触发机制生效
  - test_llm_refiner_applies_cached_corrections ：提前往 \_cache 写入高置信度修正结果，验证 apply_to_tracked() 会按缓存覆盖小模型结果
  - test_llm_refiner_ghost_detection_for_disappeared_track ：模拟 track 消失但缓存仍然存在的情况，确保能够“幽灵回写”到违章检测时对应的 bbox
    这三组测试从「触发 → 缓存 → 覆盖」完整验证了二级复核逻辑。

## 五、方向 3 / 核心方向 1：基于 Agent 的多源信息融合与预警报告生成

这部分是「工作票 + 视频违章 + 设备/站点信息 + LLM Agent」共同生成结构化预警报告。

1. 违章事件生成与结构化字段

在监控项目中，每次检测到违章事件，会调用 ViolationSender.send_violation() 存库，并传入一个 agent_report 字段：

- 关键逻辑在 main.py 中内部函数 \_generate_agent_report() 和下面的调用流程（ stream 子进程）：

```python
detected_at_dt = datetime.fromtimestamp(chosen_ts)
agent_report_content = await _generate_agent_report(
    active_ticket_no,
    site,
    stream_name,
    detected_at_dt,
    warnings_filtered,
    track_data,
)
violation_id_str = await violation_sender.send_violation(
    site=site,
    stream_name=stream_name,
    warnings_json=json.dumps(warnings_filtered),
    detection_time=detected_at_dt,
    image_bytes=chosen_frame_bytes,
    detections_json=json.dumps(track_data),
    cone_polygon_json=json.dumps(cone_polys),
    pole_polygon_json=json.dumps(pole_polys),
    agent_report=agent_report_content,
)
```

这里的数据来源已融合：

- 站点/设备信息： site 和 stream_name ，映射到 Construction-Hazard-Detection 数据库中的 Site 、 StreamConfig
- 风险事件： warnings_filtered （已做规则等级转换）
- 检测摘要： track_data （具体目标类别、数量、置信度）
- 工作票编号： active_ticket_no （由另外一条链路从工作票系统同步过来，代表当前现场对应的票）

2. Agent 报告生成的详细逻辑

\_generate_agent_report() 提供两种模式：

- Mock/Test 模式：不调用外部 LLM，只根据 warnings 拼一个固定文本（用于演示）
- 真正 Agent 模式：调用你自己的 LLM Agent 服务（Ticket Agent 服务）
  关键实现：

```python
normalized_violation = {
    'ticket_no': ticket_no or '',
    'site': site_name,
    'stream_name': stream,
    'warnings': warnings_dict,
    'detection_counts': counts_by_class,
    'top_detections': top_detections,
}
key_source = json.dumps(normalized_violation, ensure_ascii=False, sort_keys=True)
cache_key = hashlib.sha256(key_source.encode('utf-8')).hexdigest()
```

- normalized_violation 把 多源信息统一成一个结构体 ：
  - 工单信息： ticket_no
  - 设备/站点： site , stream_name
  - 风险事件： warnings
  - 检测摘要： detection_counts , top_detections
- 使用 cache*key + last_agent_report*\* 实现对同一事件的多次检测复用报告，避免重复调用 Agent 服务（节省成本，保证实时性）
  然后根据 AGENT_REPORT_MODE 环境变量决定：

- 若 mode in ('mock','test') 且有 warnings：
  - 返回类似：“【测试模式】某某站 / 某流 在 某时间 检测到风险事件：warning_no_hardhat: 2；...”
- 若是生产模式：
  - 调用工作票 Agent 服务（你自己的 LLM agent）：
    - URL： TICKET_AGENT_API_URL （默认 http://127.0.0.1:8011/api/v1/generate_violation_report ）
    - 请求 payload：

```python
payload = {
    'ticket_no': ticket_no or '',
    'enable_llm': mode not in ('api_no_llm', 'no_llm', 'without_llm'),
    'violation': {
        'site': site_name,
        'stream_name': stream,
        'detection_time': detected_at.isoformat(),
        'warnings': warnings_dict,
        'detections_summary': {
            'counts_by_class': counts_by_class,
            'top_detections': top_detections,
        },
    },
}
```

Ticket Agent 服务接口契约（Ticket API：`POST /api/v1/generate_violation_report`，默认 8011）：

- 请求：JSON（上面的 payload 结构）
- 响应：JSON，核心消费字段为 `agent_report`（字符串）

Agent 服务拿到这个 payload，结合自身对工作票系统的查询能力，可以做：

- 根据 ticket_no 拉取完整票据：时间、地点、作业内容、安全措施
- 用 violation 结构理解当前现场风险情况（例如：两人未戴安全帽，吊车靠近电杆）
- 结合安全规程知识，生成一个结构化预警报告（你可在 Agent 里定义 JSON schema）
  \_generate_agent_report() ：

- 若返回体中有 agent_report 字段（字符串），则直接使用
- 否则 fallback 为简单的「site / stream 在某时间检测到某风险事件」文本描述

3. 前端 / 记录系统中的呈现

在 examples/violation_records/routers.py 中， Violation 记录被查询时，会通过 \_get_agent_report_for_violation() ：

- 优先使用存好的 violation.agent_report
- 若为空，则根据 warnings_json 用 \_fallback_agent_report() 生成简要说明
  这样前端在展示违规记录时，可以直接看到由 Agent 生成的 语义清晰的预警报告 ，完成你要求的「结构化、语义清晰」目标。

## 六、方向 3 / 核心方向 2：自然语言视频检索与远程督查

你要实现的是类似：「查询 XX 变电站昨天下午吊车作业的视频」，系统能自动解析时间、地点、意图，并帮你把对应视频片段找出来。

在这个项目里，分两层：

1. 面向真实违规记录的检索（带站点 / 时间 / 关键词）
2. 面向 demo 视频 test3.mp4 的预计算片段检索（让用户快速体验自然语言检索）
3. 前端自然语言助手：search_assistant.js

- 入口：前端的「自然语言视频检索助手」视图
  - HTML 见 index.html
  - 文案示例已经直接用你的句式：“例如：查询 XX 变电站昨天下午吊车作业的视频”
- 核心函数： search_assistant.js 中的 runSearchFlow
  runSearchFlow() 流程：

- 获取用户输入 rawQuery ，例如“查询 XX 变电站昨天下午吊车作业的视频”
- 先判断是否走「片段检索」模式 shouldUseSegmentsMode(rawQuery) ：
  - 如果是：
    - 调用后端 /segments/intent 用 LLM/规则解析 user_query
    - 得到：
      - keyword （如 “吊车 作业”）
      - start_sec / end_sec 或多个 ranges
      - location 、真实时间 real_start_time / real_end_time
      - note （补充说明）
    - 组装「我理解的检索条件为：地点：XX 变电站 ｜ 真实时间：... ｜ 关键词：吊车 作业 ｜ 映射时间段：0-30 秒」之类的描述
    - 优先调用 /segments/clips 合并片段 → 不通再 fallback /segments
  - 如果不是（或片段模式失败）：
    - 调用 /violations/intent 解析为：
      - site_ids ：站点 IDs
      - start_time / end_time ：时间范围
      - keyword ：关键词
      - query_mode ：例如按违章记录搜索
    - 结合前端缓存的站点列表 fetchMySitesForSearch() 推断站点名称
    - 如果 intent 里没有时间，就用 parseTimeRangeFromQuery(rawQuery) 从自然语言中补时间（例如“昨天下午”）
    - 最终形成描述：「站点：XX 变电站 ｜ 时间：2026-01-27 13:00-18:00 ｜ 关键词：吊车作业」
    - 再去走后续的违章记录检索（对应另一个 routers 里的查询接口）
      这一整段就是你要求的「自然语言指令 → 检索条件」。

2. 后端：片段检索（test3.mp4 demo）

- 自然语言 → 片段意图解析

  - 函数： routers.py 中 \_parse_segments_intent
  - 核心功能：

    - 解析 “从 3 秒到 10 秒” 这样的明确时间范围（正则识别「X 秒到 Y 秒」）
    - 支持“前 10 秒”、“最后 5 秒”等相对描述
    - \_parse_real_datetime_range(text, now) 识别“昨天下午”等自然语言时间区间
    - \_extract_demo_location(text) 提取地点关键词

  - 对外暴露为 /segments/intent ：

    ```python
    @router.get('/segments/intent')
    async def get_segments_intent(user_query: str = Query(..., min_length=1)) -> dict:
        return _parse_segments_intent(user_query)
    ```

  - 响应（关键字段）：
    - `keyword`: 关键词（从 query 清洗得到）
    - `start_sec/end_sec`: 映射到 `test3.mp4` 的时间窗（可能为空）
    - `ranges/time_ranges`: 多段时间窗（可能为空）
    - `location`: demo 地点关键词（可能为空）
    - `real_start_time/real_end_time`: 若识别出“昨天下午”等真实时间，会返回并进行循环映射
    - `duration_sec`: demo 视频长度

- 片段搜索与合并：

  - 数据来源： test3_segments_generator.py 预先对 test3.mp4 做分割、图像导出，保存在 examples/violation_records/static/test3_segments ，索引信息写到 test3_segments.json
  - 片段检索接口：

    - /segments : 返回原始片段
    - /segments/clips : 将相邻片段合并为更长的 clip，支持 merge_gap_sec 、 max_clips
    - 这些接口内部调用 \_filter_segments() 和 \_merge_segments_to_clips() ，按 keyword 、时间范围过滤后再合并

  - /segments/clips 接口契约（演示检索）：
    - Query：
      - `keyword`（可选）
      - `start_sec/end_sec`（可选）
      - `range`（可选，可多次；形如 `3.000-10.000`）
      - `merge_gap_sec`（默认 0.2）
      - `max_clips`（默认 10）
    - 响应：`list[dict]`，每个元素核心字段：
      - `clip_id`、`start_sec`、`end_sec`、`segments_count`、`segment_ids`
      - `thumbnail_url`（用于展示截图）
      - `video_url`（固定为 `/segments/video`，前端通过 `#t=start,end` 控制播放区间）

- 前端播放：

  - buildClipsResultsNode / buildSegmentsResultsNode 负责构建结果列表，提供：
    - 点击播放按钮在浮层中加载 /segments/video ，并带 #t=start,end 给浏览器控制播放区间
    - 缩略图： thumbnail_url / image_url 加载 /segments/image 提供截图
      所以，当用户在演示模式下输入：
      “开头的片段”、“最后的片段”、“吊车 作业”
      系统会通过 /segments/intent 把这些自然语言映射到 test3.mp4 的某些时间段，再通过 /segments/clips 查出对应片段并在前端播放。

3. 后端：基于真实违规记录的自然语言检索

- Intent 解析：

  - routers.py 中 /violations/intent（默认 8002，需要 JWT）
  - \_parse_intent_with_llm(user_query, sites) ：用 LLM 根据用户可访问站点列表解析意图（站点、时间、关键词等）
  - 若 LLM 失效，则 fallback \_fallback_intent_by_sites() ，用简单规则从 query 和 site 名匹配

  - /violations/intent 响应（Pydantic 模型 ViolationsIntent）：
    - `site_ids`: 站点 ID 列表（已按权限过滤）
    - `site_names`: 站点名称列表（与 `site_ids` 对应）
    - `keyword`: 关键词（可能为空）
    - `start_time/end_time`: ISO 时间范围（可能为空）
    - `query_mode`: 当前固定为 `search`
    - `confidence`: 0-1（可能为空）

- 站点安全过滤：

  - 根据 JWT 用户信息，从数据库查出他有权限访问的 Site
  - Intent 中的 site_ids 必须在 allowed_ids 中才有效
    后续真正的记录检索接口（查询违规记录）会根据：

- site_ids ：过滤到具体变电站/工地
- start_time / end_time ：过滤到指定时间段（如“昨天下午”）
- keyword ：如“吊车作业”、“未戴安全帽”等
  再结合搜索工具类（如 search_utils.py 中用 CKIP 分词、同义词扩展）真正查库。
  最终呈现给前端的结果列表里，除了时间/站点/场景图片，还可以点击进入播放原始视频或对应片段，实现远程督查和回放。

## 8. 常见排障

- Ticket OCR/NER 直接报错：优先检查 `ticket/service/config.py` 中的 Python 路径与虚拟环境是否存在
- `/violations/intent` 或 `/upload` 返回 401：JWT 无效或未携带；需先走登录获取 token
- `/upload` 返回 403：当前用户没有该 `site` 的权限，检查用户与站点绑定关系
- demo 片段检索无结果：确认 `examples/violation_records/static/test3_segments.json` 存在且对应 `test3.mp4`
- 二级复核不触发：检查 `LLM_REFINE_ENABLED`、阈值与 `LLM_REFINE_CLASSES` 配置；同时确认 `ALIYUN_API_KEY` 配置有效
